# 백엔드 개선 계획

**목표** · 현재 React·Phaser 프론트를 FastAPI·MySQL 8 백엔드에 연결해 실제 강의 수강부터 시험, AI 채점, 결과 확인까지 검증하고 운영 중 제출·채점 기록을 보호합니다.

**기준** · [API 명세](../../2_API명세서.md), [ERD](../../1_ERD.md), [MVP 계획](../../백엔드_MVP_개발계획.md), [실제 모델 검증](../../실제_AI_채점_검증.md), 프론트 `src/api`와 `src/game/net`의 현재 인터페이스.

**검토 범위** · 2026-11-20 기준 로컬 `backend/feat/backend-mvp` 작업 트리, `frontend/main`, 로컬 MySQL 8, 기존 실제 모델 검증 기록. 백엔드 테스트 46개, Alembic 스키마 검사, 잠금 파일 검사가 통과했습니다. 앞선 프론트 테스트 228개와 모의 서버 검사 120개는 프론트 기준 동작을 보여줍니다. 실제 연결에서는 Vite를 거친 직무 목록 조회를 검증했고, 전체 사용자 흐름은 아래 완료 기준으로 잡았습니다. 백엔드 코드와 DB 데이터는 이번 점검에서 수정하지 않았습니다.

## 유지할 서비스 규칙

- 연결된 강의에서 중복을 뺀 시청 구간이 실제 길이의 80% 이상일 때 해당 시험을 열고, 시작 API에서 다시 확인합니다.
- 새 응시는 실무 과제 해결과 AI 활용 역량을 모두 충족해야 통과합니다. 실무 필수 요건과 AI 답변 검증 최소 점수를 유지합니다. 기존 `LEGACY_TOTAL_V1` 결과는 저장된 기준으로 표시합니다.
- 현재 프론트가 사용하는 `/api/v1`, 쿠키 기반 토큰 재발급, 결과 폴링, Phaser 픽셀 좌표 규격을 기준으로 합니다. 프론트 동작을 바꾸는 시험 마감·결과 확인 정책은 명세와 계약 테스트에 함께 반영합니다.
- 검수는 무역 사무 직무부터 시작합니다. 콘텐츠 추가와 다중 서버 확장은 해당 단계의 완료 기준으로 진행합니다.

## 구현 순서

### 1. 실제 프론트 계약 고정과 첫 통합 검수 · P0

대상 파일 `app/api/map_ws.py`, `app/services/presence.py`, `.env.example`, `README.md`, `docs/2_API명세서.md`, `tests/test_map_ws.py`, `tests/test_entrypoint.py`.

- [ ] 프론트와 채택할 계약을 샘플 메시지로 고정합니다. `move`, `snapshot.me`, `snapshot.players`, `player_joined`, `player_moved` 모두 `x/y/dir`을 사용합니다. 기본 범위는 두 축의 0부터 맵 너비·높이까지, 기본 시작 상태는 `(960, 880, down)`입니다.
- [ ] 실제 프론트 메시지 `{type: "move", x: 980, y: 900, dir: "right", moving: true}`를 보냈을 때 상대가 같은 좌표와 방향을 받는 테스트를 추가합니다. 경계값, 비수치 좌표, 알 수 없는 방향, 이동 제한, 5초 인증, 같은 계정 중복 접속, 레벨 이벤트도 검증합니다.
- [ ] 개발 프록시 주소를 `http://127.0.0.1:8000`으로 문서화하고, 실제 Vite 프록시를 경유한 HTTP 및 WebSocket 검사를 실행합니다. HTTP 계약은 상태 코드·필수 필드·에러 코드·빈 응시 204·쿠키 재발급까지 비교합니다.
- [ ] 기존 작업 트리 변경을 검토하고, 실행 코드·마이그레이션·명세·테스트를 재현 가능한 변경 집합으로 정리합니다. 로컬 환경 파일·자격 증명·가상환경의 Git 제외를 검사하고 팀 브랜치에서 통합 검수가 가능하도록 합니다.

### 2. 커리큘럼과 수강 신뢰도 · P0/P1

대상 파일 `scripts/seed.py`, `app/api/lectures.py`, `app/services/progress.py`, `app/api/tasks.py`, `app/models/__init__.py`, `tests/test_progress.py`, `tests/test_database.py`, 필요한 새 Alembic 리비전.

- [ ] 첫 검수는 승인된 무역 사무 강의 1개와 연결 시험 1개로 완주합니다. 공개할 영상 ID, 삽입 재생 가능 여부, 실제 길이, 시험 지시·자료·루브릭을 함께 확인합니다.
- [ ] 이후 모의 프론트에서 제시하는 5개 과정은 실제 콘텐츠 준비 현황에 맞춰 안정적인 키와 버전으로 등록합니다. 콘텐츠 가져오기는 재실행 가능하게 만들고 양수 영상 길이, 동일 직무의 강의·과제 연결, 자료 순서, 필수 요건 ID 유일성, 배점·합격선 범위를 검증합니다.
- [ ] 79.9%와 정확히 80%, 중복 재생·탐색·다른 직무 및 연결 강의, 끝까지 재생한 영상의 80% 도달을 확인합니다. 표시상 80%와 실제 자격 판정이 갈릴 때 UI·API 해석이 일치하도록 정밀도 계약을 정합니다.
- [ ] 수강 기록은 서버 시간으로 제한한 브라우저 보고입니다. 높은 신뢰도의 수강 증명이 필요한 운영이라면 세션 단위 짧은 보고 주기·유휴 시간 상한·중복 세션 정책을 추가합니다. 재연결과 백그라운드 재생까지 시나리오로 검증합니다. 영상 교체 시 기존 진행 중인 학습·완료 기록을 어떤 버전에 유지할지도 정합니다.

### 3. 서버 마감과 복구 가능한 채점 · P1, 대외 시범 전

대상 파일 `app/api/attempts.py`, `app/services/attempts.py`, `app/services/grading.py`, `app/main.py`, `app/models/__init__.py`, 신규 작업 실행 모듈·마이그레이션, `tests/test_attempts.py`, `tests/test_concurrency.py`, `tests/test_mvp_flow.py`.

- [ ] 마감 전, 마감 직후, +60초 경계와 유예 만료 후의 저장·수동 제출·자동 제출·포기 규칙을 표로 고정합니다. 권장 정책은 마감 전에는 제출 본문을 받고 마감 후 유예에는 마감 전 서버에 저장된 마지막 답안을 확정하는 방식입니다. 프론트가 마감에 보내는 마지막 본문의 처리 방식과 저장 안내를 계약에 포함합니다.
- [ ] 사용자 요청 없이 만료 응시를 찾는 작업을 추가합니다. 마감 이후 포기로 제출 대상이 사라지는 경우를 막고, 수동·자동 제출 동시 실행과 요청 재시도에서 답안·작업이 한 번만 확정되는 테스트를 추가합니다. 마감 전 포기의 이력 보존이 필요하면 삭제 대신 `ABANDONED` 상태를 검토합니다.
- [ ] MVP 배포는 기존 MySQL에 채점 작업을 저장하는 구조를 제안합니다. 응시 상태 변경과 작업 등록을 같은 트랜잭션에 두고 작업에 시도 횟수, 다음 실행 시각, 처리권 만료, 작업 실행 식별자를 둡니다. 현재 처리권을 가진 작업만 최종 점수와 레벨을 확정하게 합니다.
- [ ] 일시적 모델·DB 오류는 횟수를 제한해 재시도하고, 루브릭·입력 오류나 재시도 종료는 원인 분류와 함께 `GRADING_FAILED`로 남깁니다. 응시 API의 기존 상태 값과 결과 조회 흐름을 유지합니다.
- [ ] 브라우저를 닫아도 자동 제출, 커밋 직후 프로세스 중단 후 복구, 두 작업자 경쟁, 실패 후 재채점, 작업 재실행 후 점수·레벨 중복 없음, 기존 데이터 마이그레이션을 검증합니다.

### 4. 채점 근거, 콘텐츠 버전, 요청 일관성 · P1, 대외 시범 전

대상 파일 `app/services/ai.py`, `app/services/grading.py`, `app/services/grade_output.py`, `app/services/results.py`, `app/api/attempts.py`, `app/api/schemas.py`, `scripts/validate_live_grading.py`, `tests/test_ai_provider.py`, `tests/test_grading.py`, `tests/test_attempts.py`.

- [ ] 양수 검증 점수는 AI 답변 이후 작성한 학습자의 대화 또는 실제 수정 기록에만 허용합니다. 같은 응시 소속, 작성 주체, 순서, 원자료와 대조한 내용 검사를 분리합니다. AI 대화가 없거나 AI 전 초안만 있는 경우, AI 답변 그대로 복사, 형식만 수정, 관련 없는 후속 질문, 실제 원자료 대조를 각각 시험합니다.
- [ ] 응시 시작 시 과제 설명·자료·루브릭 버전을 고정하고 이어 풀기와 재채점에 같은 입력을 사용합니다. 기존 응시는 당시 자료를 확인할 수 있는 경우에만 복원하고 확인할 수 없는 기록은 출처 상태를 표시합니다. 채점 실행에는 모델·프롬프트 버전, 구조화된 대화·수정 근거와 실패 이유를 기록합니다.
- [ ] 모델에 주는 점수 예시는 해당 루브릭에서 계산합니다. 과제별 필수 사실은 구조화할 수 있는 부분부터 서버가 대조하고, 모델 결과는 근거와 점수 범위로 검증합니다. 요구한 결과물과 무관한 사용자 입력, 장애, 상·하한 점수, 긴 한국어 입력도 검사합니다.
- [ ] 응시별 한 번의 진행 중 AI 대화를 허용하고, 요청 식별자를 재전송하면 같은 결과를 돌려주는 흐름을 검증합니다. 답안 자동 저장은 최근 버전이 유지되도록 조건부 갱신을 도입합니다. 채팅·채점의 입력 예산, 답안 수정·이벤트 상한, 결과 보존 기간을 정하고 채점에 필요한 근거를 보존합니다. 모델 호출 한도나 지연에 도달한 경우 복구 가능한 응답으로 처리합니다.
- [ ] 실제 모델 평가 표본을 공개 과제별로 만들고 사람이 확인한 기대 판정을 둡니다. 양쪽 충족·한쪽만 충족·검증 미달·필수 요건 누락·합격선 경계·긴 이력 결과를 반복 확인합니다. 프롬프트·모델을 바꿀 때 합격 판정, 거짓 통과, 근거 일치와 처리 시간을 비교합니다.

### 5. 세션, 운영 환경, 지속 검증 · P1/P2

대상 파일 `app/api/auth.py`, `app/api/dependencies.py`, `app/services/auth.py`, `app/api/map_ws.py`, `app/main.py`, `app/settings.py`, `app/db.py`, `README.md`, 신규 CI·배포 설정.

- [ ] 로그아웃과 계정 상태 변경을 API·WebSocket에 반영하는 정책을 정합니다. 권장안은 세션 식별자로 폐기를 추적하고, 연결은 폐기나 토큰 만료 시 재인증하도록 하는 방식입니다. 응답 유실이나 여러 탭에서 생긴 정상 갱신 경합의 처리 규칙을 먼저 고정하고, 정책상 재사용으로 판단한 경우 해당 토큰 계열만 폐기하고 보안 이벤트를 남깁니다. 로그아웃 직후 기존 토큰 거부, 별도 세션 유지, 회전·경합을 검증합니다. 만료·폐기된 세션 기록을 보존 기간에 맞춰 정리합니다.
- [ ] 로그인, 회원가입, AI 호출, 채점 재시도, WebSocket 연결·메시지에 서비스 한도를 설정합니다. HTTP는 한도를 초과하면 `429`와 재시도 대기 시간을 반환하고 정상 자동 저장 주기를 허용합니다. HTTPS/WSS, 같은 출처 프록시, 요청 크기와 WebSocket 출처 검사를 배포 환경에서 확인합니다. 토큰·답안 본문·원자료를 로그나 모니터링에 남기지 않도록 검토합니다.
- [ ] 팀 CI에서 MySQL 8 초기 마이그레이션과 기존 버전 업그레이드, 백엔드 테스트, 실제 계약 검사, 잠금 파일을 검증합니다. 모델이 필요한 시나리오는 고정 모델 환경에서 별도 실행합니다. 스테이징에서 DB 복구, 마이그레이션 롤백 전략, 장애 시 복구 순서를 연습합니다.
- [ ] 프로세스 생존, DB 준비 상태, 채점 작업 진행 상태를 따로 알 수 있게 합니다. 배포 검수에서 AI 설정과 모델의 구조화 응답 지원을 확인하고, 모델 장애 중에는 학습·결과 조회와 채점 가능 상태를 따로 표시할 수 있게 합니다. 요청 식별자와 응답 지연, 작업 대기량·오래된 작업, 채점 실패 원인, WebSocket 종료율을 측정합니다. 반환된 오류에는 요청 추적에 필요한 정보만 담습니다.
- [ ] 초기 운영은 맵 API 단일 프로세스로 유지하고 채점 작업 실행을 분리합니다. 목표 동시 사용자 수로 폴링·맵·AI·DB를 함께 부하 시험하고 느린 쿼리와 인덱스를 측정해 조정합니다. 다중 인스턴스로 확장할 때 공유 접속 상태와 이벤트 발행, 중복 접속 처리부터 검증합니다.
- [ ] 결과 최초 조회에 실패하거나 응답이 유실되면 프론트에 최초 확인 알림이 누락될 수 있습니다. 사용자 확인까지 알림을 유지해야 하는 운영이라면 조회와 확인 처리를 분리하고, 재요청·두 탭·오프라인 복귀에서 각각 가능 상태를 검증합니다.
